# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ImapKit (`imapkit` on npm) is a scriptable, in-memory IMAP4rev1 mock server for client integration testing. Nothing touches disk: the whole mailbox tree comes from a JSON `storage` object at construction time, so every new server instance starts from a clean state. Written in TypeScript under `src/` and published as a dual package (ES modules in `dist/esm/`, CommonJS in `dist/cjs/`, each with type declarations), callback style, supports Node.js 20 and newer (`engines` in package.json; CI tests 20, 22 and 24) and the latest Bun and Deno (CI runs the whole suite on both).

## Commands

- `npm test`: ESLint and the type check (`npm run lint`), the build, then all tests (`npm run test:unit`, which is `node --import tsx --test test/*.test.ts`; tests import `src/` directly through tsx, only `test/package.test.ts` and `test/cli.test.ts` need the built `dist/`).
- `npm run build`: `scripts/build.js` generates `src/cert.ts` from `cert/` (gitignored), compiles `src/` with `tsconfig.esm.json` and `tsconfig.cjs.json`, makes `require()` of a module with a default export return that export with the named exports as its properties (the pre-TypeScript CommonJS shapes: `require('imapkit')` is the factory with `TAG_REGEX`), collects the `@help` lines of the plugins into `dist/plugin-help.json` for `imapkit --help`, and bundles `dist/esm` with esbuild into `dist/browser/imapkit.js` (the `imapkit/browser` export), replacing the Node builtins with the shims in `scripts/browser/` (`BROWSER_SHIMS` in the build script; a new `node:` import fails the build until it has a shim). Buffer and EventEmitter come from the `buffer` and `events` devDependencies, `setImmediate` is a MessageChannel, sockets, TLS, the REST API and SMTP throw, and the COMPRESS plugin is replaced with one that throws (`BROWSER_MODULES`, the build fails if a listed module is not found). `prepare` runs it on install and publish.
- `npm run test:bun`, `npm run test:deno`: the suite under Bun and Deno. Deno does not pass a `done` callback to `node:test` hooks, so hooks return promises.
- `npm run test:coverage`: the tests with Node's built-in coverage for `src/` (Node >= 22.8). Fails below 94% line coverage; CI runs it on Node 24.
- Single test file: `node --import tsx --test test/uid-fetch.test.ts`. Single test case: add `--test-name-pattern="<test name>"`.
- `npm run lint`, `npm run format` / `npm run format:check` (Prettier: single quotes, 4 spaces, 160 columns). CI fails on unformatted files. `npm install` sets `core.hooksPath` to `.githooks`, whose pre-commit hook runs Prettier on staged files.
- `npm run update`: refresh all dependencies to latest (`ncu -u`, config in `.ncurc.cjs`, which keeps `@types/node` on 20.x and `typescript` on 6.x). Dependencies are pinned to exact versions.
- `npm run dovecot:start` then `npm run compare -- <scenario>`: compare ImapKit with Dovecot (see "Comparing with Dovecot" below).
- Run the server (after `npm run build`, the command loads `dist/`): `node bin/imapkit.js -p 1143 --plugin=IDLE,MOVE --debug` (see `bin/help.txt`; options also come from `IMAPKIT_*` env vars, `--config`, `--storage`, `--smtpPort`). Default login is `testuser` / `testpass`.

ESLint (`eslint.config.js`, with typescript-eslint) enforces `const`/`let` (no `var`), arrow callbacks, one declaration per statement and `===`.

## TypeScript and module format

- Every file under `src/` compiles both as ES module and as CommonJS, so it must not use `import.meta`, `require`, `module`, `exports`, `__dirname`, `__filename`, top-level `await` or JSON imports. Relative imports carry the `.js` extension, builtins use the `node:` prefix. Tests are ES modules and may use `import.meta.url`.
- `tsconfig.base.json` is strict (`noImplicitAny`, `exactOptionalPropertyTypes`), `erasableSyntaxOnly` is on (no enums, no parameter properties), `@types/node` stays on 20.x so APIs newer than Node 20 do not type-check. Optional properties of exported option types are declared with an explicit `| undefined`.
- Shared types live in `src/types.ts` (`Message`, `Mailbox`, `ParsedCommand`, `CommandHandler`, `Plugin`, the hook types ...). `IMAPServer` and `IMAPConnection` have an index signature for the state plugins keep on them, plus `declare`d fields for everything the core uses. IMAP attribute trees (parsed commands, responses) use the open `Attribute` alias.
- The package root (`src/index.ts`) default-exports the `imapkit(options)` factory, which also carries `TAG_REGEX`, `IMAPServer` and `IMAPConnection` as properties, and exports the types. `package.json` `exports` maps `.`, `./lib/server` and `./lib/*` to both builds, so the old deep imports (`imapkit/lib/plugins/idle`) keep working; `test/package.test.ts` checks the shapes.

## Releases

Releases are automated with release-please (`release-please-config.json`, `.release-please-manifest.json`): use Conventional Commit messages (`fix:`, `feat:`, `chore:` ...) on master, merge the release PR it opens, and `.github/workflows/release.yaml` waits for the `test.yml` run on that commit and then publishes to npm through trusted publishing (OIDC, no token). ## Strict by design

ImapKit is a guardrail for developing standards compliant IMAP clients, so it follows the RFCs strictly instead of being lenient like production servers (WildDuck, Dovecot). When a client breaks a MUST or the grammar, answer BAD (or NO where the RFC says so) instead of guessing what it meant. The rules in force are listed in the README "Strict by design" section and covered by `test/conformance.test.ts`.

Always check RFC text against the real source document at `https://www.rfc-editor.org/rfc/rfcXXXX.txt` (XXXX is the RFC number), never from memory, and cite the section in code comments and tests.

## Architecture

Almost everything lives in `src/server.ts`, which defines two classes:

- **`IMAPServer`**: holds the shared single-user storage, registered capabilities, command handlers, and the plugin extension arrays. Builds `folderCache` (path to mailbox object) via `indexFolders()` / `processMailbox()` from the namespace-keyed `storage` object (keys like `"INBOX"`, `""`, `"INBOX."`, each with `separator`, `type`, nested `folders`, `messages`). Subscriptions are names in `server.subscriptions`, not part of the mailbox objects (`mailbox.subscribed` is an accessor for it, see `trackSubscription()`), so they survive DELETE and stay with the old name on RENAME; `getSubscriptionTree()` gives LSUB and `LIST (SUBSCRIBED)` the subscribed names, with `\Noselect` stand-ins for names that are not mailboxes. Cross-connection updates go through `server.notify()`, which emits a `notify` event that every connection listens to; `server.notifyFilters` (`filter(connection, notification)`) lets a plugin keep a notification from some connections (ACL does for METADATA). Every notification carries `origin`, the session whose command caused it (`server.activeConnection` while a command handler runs, null for SMTP), and the EXISTS of a new message carries the `message`.
- **`IMAPConnection`**: one per socket. Parses lines and literals with `imap-handler`, queues commands (`scheduleCommand` / `processQueue`, strictly one at a time), refuses commands in the wrong state, with arguments when they take none, and mailbox name arguments that are not valid modified UTF-7 (options from `src/command-states.ts` or `setCommandHandler`, checked centrally in `processQueue`, not per handler), refuses ambiguous pipelining (RFC 3501 5.5), tracks `state` (`"Not Authenticated"`, `"Authenticated"`, `"Selected"`), `username` (set by LOGIN and the AUTHENTICATE plugins) and `selectedMailbox`, and buffers notifications from other connections, flushing them before tagged responses and, for commands that refer to messages, before the command runs (`processNotifications(data, beforeCommand)`): new-message EXISTS (followed by RECENT for IMAP4rev1 sessions) and flag updates go out first, EXPUNGE waits during FETCH/STORE/SEARCH (`noExpunge`, RFC 3501 section 7.4.1) together with everything queued after it, and the tagged OK then carries `[EXPUNGEISSUED]`. Messages expunged by another session stay in the session's view (`getSessionMessages()`, marked `ghost`) until the EXPUNGE is reported; README "Multiple sessions" lists the RFC 2180 strategies FETCH, STORE, SEARCH, COPY, MOVE, DELETE and RENAME follow. `connection.inputHandler` lets a plugin (e.g. IDLE, AUTHENTICATE) take over raw input lines, and a plugin can override `connection.canSetSeen()` (FETCH sets `\Seen`) and `connection.canExpunge()` (CLOSE expunges), both `!readOnly` by default, as ACL does. All output goes through `connection.write()` (also raw `+` continuations) and `connection.end()` closes after the output is written, never `connection.socket.write/end`: `connection.transport` is an optional layer between the protocol and the socket with `write`, `receive`, `end(callback)` and `destroy`, which passes data on with `connection.writeRaw()` and `connection.onData()`, so it is always above TLS (COMPRESS uses `src/deflate-layer.ts`, which the mock client, the session helper and the compare tool share). `connection.resetSession()` returns to the Not Authenticated state (UNAUTHENTICATE, RFC 8437), `connection.discardInput()` drops unprocessed input. LITERAL+ and LITERAL- set `server.literalPlus` and `server.nonSyncLiteralLimit`.

**Store operations and control API**: `src/store-operations.ts` holds the changes that commands and the control API share: `expungeMessages` (`connection.expungeSpecificMessages` calls it), `notifyFlagChanges`, `changeFlags` (flag changes outside STORE, emits the `flags` event `(mailbox, messages, origin)` that CONDSTORE uses to bump MODSEQ; STORE keeps its own path because of UNCHANGEDSINCE), and `deleteMailbox` (with BYE for other sessions), `renameMailbox`, `subscribeMailbox`, `unsubscribeMailbox`, which the commands of the same name call. They throw `ImapKitError` (`storeError()`, also used by `server.createMailbox` and `server.deleteMailbox`) with a RFC 5530 `code` or `INVALID`, and take the origin from `server.activeConnection`, which `server.withOrigin(origin, fn)` scopes (`processQueue` runs a handler with its session, the control API with null). `src/control.ts` is `server.control` (README "Control API"): it checks every argument and runs each change through `withOrigin(null, ...)`, so sessions see it like a change from another session. The `command` event and the `session` events `login` and `logout` go out from `send()` when the tagged response of the command goes out (`commandCompleted`, comparing with `connection._commandStart`), `select` from SELECT, `unselect` from `connection.closeMailbox()`, `waiting` from `processQueue` when a command takes over input (IDLE, AUTHENTICATE), `open` and `close` from the connection. Plugins add control operations and REST routes with `server.control.register(name, fn, routes)` (ACL, QUOTA, METADATA) and put non-JSON data into `snapshot()` with `server.control.snapshotHandlers` (ACL); `server.control` exists before the plugins load. Plugin data that follows mailbox changes (ACL and annotations on DELETE, ACL inheritance on CREATE through the `created` list of the event, annotations on RENAME INBOX) is handled in `mailbox` event listeners, never in command wrappers, so the control API gets the same behavior. Script rules also have the `quiet` event (`quietFor`, timers in `connection.watchQuiet()`, every input and output calls `connection.touch()`), `chance` (random numbers of `server.script.random`, seeded with `scriptSeed`, see `src/random.ts`) and `chunkDelay: 'tick'`. `src/quirks.ts` holds the quirk presets of the `quirks` option (script rules and plugins to leave out). `server.now()` (the `now` option) is the clock of the dates the server sets. `src/storage-schema.ts` checks the `storage` option in `loadStorage()` (types of the known keys, typos of them; plugin keys stay allowed, add a new plugin storage key to `PLUGIN_KEYS` there) and exports the JSON Schema. `connection.describe()` is the session description of `sessions()` and the events, `connection.isOpen()` tells if output can still be sent. `server.connect({ secure })` opens a connection without a socket through `src/memory-socket.ts` (a pair of `MemorySocket` ends, the client end is returned), which is how the browser bundle is used (README "Run in a browser", the docs "Try it live" page, `examples/browser.html`, `test/connect.test.ts`, `test/browser.test.ts` runs the bundle in a `vm` context with only browser globals). A socket with `encrypted: true` (like `tls.TLSSocket`) makes the session count as TLS, and STARTTLS calls `socket.startTls(callback)` when the socket has it instead of adding a TLS layer (MemorySocket only sets the flag). Code that the bundle runs must not need Node-only globals at run time: guard `unref()` (`timer.unref?.()`) and `process`. `server.start()` / `server.stop()` are the promise forms of `listen()` / `close()`, `start()` also starts the SMTP listener of the `smtp` option. smtp-server is an optional peer dependency (and a devDependency for the tests): only `src/smtp-listener.ts` imports it, loaded with a dynamic `import()` by `server.loadSmtpListener()` and by the CLI for `--smtpPort`, so `require('imapkit')` never loads it (`test/package.test.ts` checks this). `src/rest.ts` is the REST API (README "REST API", `rest` option, `--rest-port`): a route table over `server.control` on `node:http`, which also generates `GET /v1/openapi.json`. `GET /v1/events` streams server events as Server-Sent Events (a route handler can return `{ stream(res, req) }`). Its access rules are deliberate: loopback by default, a token for any other address, a loopback Host header without a token (DNS rebinding), JSON bodies only and no CORS headers (no cross-origin requests from browsers).

**Commands** (`src/commands/`): each file default-exports a `CommandHandler`, `function(connection, parsed, data, callback)`. `src/commands/index.ts` maps command names to them (`'UID FETCH'` is `uid-fetch.ts`), and `getCommandHandler()` takes a built-in handler from there the first time a command is used; a new built-in command has to be added to that registry. A handler must send a tagged response with `connection.send(response, description, parsed, data, ...extra)` and then call `callback()`, or the connection's queue stalls. Per-item FETCH/STORE/SEARCH logic is in `src/commands/handlers/`.

**Plugins** (`src/plugins/`): enabled via `options.plugins` (string names map to lowercase filenames through the registry in `src/plugins/index.ts`, where a new built-in plugin has to be added, or a function). The `@help` lines of a plugin's doc comment are its `imapkit --help` text. Each receives the server and extends it only through:

- `registerCapability(name, availabilityFn)`, `setCommandHandler` / `getCommandHandler` (wrap the existing handler to override a built-in command)
- `server.fetchHandlers`, `searchHandlers`, `storeHandlers`, `statusHandlers` (consulted before the built-in handlers in `commands/handlers/`), `fetchFilters`. A fetch handler with `setsSeen = true` sets `\Seen` like `BODY[]`, and one that throws an error with `imapResponse = 'NO'` and `code` fails the FETCH with `NO [code]`. FETCH sends nothing until every message is done, so a failed FETCH has no untagged output and no `\Seen` changes. A new STATUS item also goes into `server.allowedStatus` (the `DELETED` item is built in, QUOTA allows it for every session, IMAP4rev2 only after `ENABLE IMAP4rev2`)
- `server.searchHandlers` keys normally take string arguments (one per handler param after `connection, message, index`); a handler with an `argumentTypes(list)` method decides its own arguments, and a type can be a parse function that throws `badError` (see MODSEQ in `condstore.js`). The untagged SEARCH response passes the search result `{ list, numbers, keys }` as `extra`, which is how ESEARCH replaces it and CONDSTORE adds `(MODSEQ n)` (the ESEARCH response passes the same object, with `list` holding only the returned messages). ESEARCH response building lives in `src/esearch.ts`; IMAP4rev2 makes a plain SEARCH answer with ESEARCH by setting `parsed.searchReturn` to an empty Map. The search result also has `matches(message, index)`, which checks a message against the same criteria later (CONTEXT=SEARCH updates), and `makeSearch` takes an optional range resolver to search a mailbox that is not selected (MULTISEARCH)
- Result options (`RETURN (...)`) are a registry in the ESEARCH plugin: `server.searchReturnOptions` (name to `{ data, response, hint, once, parse }`), `server.searchReturnChecks` for invalid combinations, `server.parseSearchReturn()` and `server.acceptSearchReturn(command)` for commands that take them (ESORT adds SORT). `parsed.searchReturn` is a Map of option name to argument (PARTIAL has its parsed range)
- SORT passes `{ ...searchResult, sorted, compare }` as `extra` of the `* SORT` response, `server.sortComparator(criteria)` sorts again later (CONTEXT=SORT)
- `connection.getMessageRange(range, isUid)` resolves every sequence set argument; SEARCHRES replaces it per connection (via `connectionHandlers`) to support `$`. A sequence set that does not start with a number or `*` does not count as sequence numbers for the RFC 3501 section 5.5 pipelining check
- extended LIST options: the registry from `getListExtensions(server)` in `src/list-extensions.ts` holds the selection and return options that the LIST-EXTENDED plugin accepts; SPECIAL-USE and LIST-STATUS add theirs there, in any load order
- `server.messageHandlers` (run on every message in `processMessage`), `mailboxHandlers` (run on every mailbox in `processMailbox`), `connectionHandlers` (run on new connections), `resetHandlers` (run by `connection.resetSession()`; a plugin that keeps per-session state on the connection MUST clear it here, RFC 8437 section 4.1), `outputHandlers` (can mutate or suppress any outgoing response via `response.skipResponse`; the `description` string passed to `send` is how they identify responses)
- the `expunge` event, `server.on('expunge', (mailbox, messages, connection) => ...)`, emitted by `expungeSpecificMessages` before the EXPUNGE notifications (each of which carries the removed `message`, and a VANISHED notification of QRESYNC the `messages`; CONTEXT=SEARCH sends REMOVEFROM before them), and per connection overrides of `connection.prepareNotifications(queue)` (QRESYNC turns EXPUNGE into VANISHED there), `connection.queueNotification(command, notification)` (NOTIFY drops unwanted events of the selected mailbox and flushes the queue between commands there) or `connection.getMessageRange` (SEARCHRES)
- the `mailbox` event, `server.on('mailbox', ({ type, path, oldPath, mailbox, origin }) => ...)`, emitted through `server.mailboxChanged()` by CREATE, DELETE (with the removed `mailbox`), RENAME (with `oldPath`), SUBSCRIBE and UNSUBSCRIBE (only when the subscription changed), and the `acl` event `(mailbox, previousAcl)` of SETACL and DELETEACL; `server.acl.getRights(connection, mailbox, [acl])` and `server.condstore` let other plugins check rights and CONDSTORE state. `statusResponse()` in `commands/handlers/status.ts` and `fetchResponse()` in `commands/fetch.ts` build STATUS and FETCH responses for unsolicited use (NOTIFY)
- `server.closedChecks` (`check(connection)`, SELECT and EXAMINE send `* OK [CLOSED]` when they close the selected mailbox if any is true; CONDSTORE always, IMAP4rev2 for enabled sessions)
- `appendChecks` (can veto APPEND, COPY and MOVE before messages are added, through `connection.checkAppend`, e.g. QUOTA's `NO [OVERQUOTA]`), `copyHandlers` (carry properties of the source over to the copy in `server.copyMessage`, for COPY, MOVE and RENAME INBOX, before the message handlers run)
- APPEND hooks, used by APPEND and REPLACE through `prepareAppend()` / `storeMessages()` in `src/commands/append.ts` (all messages are parsed, built and checked before any is stored, so a failure changes nothing): `server.appendDataHandlers[LABEL]` parses an append-data extension such as CATENATE and returns a function that builds the message source, then `server.appendChecks` run on the built messages of the whole command (their options are `{ command, replaced }`, `replaced` is the message REPLACE removes, while COPY and MOVE pass `{ move, source }`), `server.multiAppend` (set by MULTIAPPEND), `server.urlAccessChecks` (`(connection, mailbox, url)`, return `{ text }` to refuse a CATENATE URL with `NO [BADURL]`, e.g. for ACL), `server.searchAccessChecks` (`(connection, mailbox, named)`, return false to leave a mailbox out of a MULTISEARCH ESEARCH, ACL uses it), and `server.literalFilters` (`(connection, command, line, size)`, can refuse a synchronizing literal before it is read by returning `{ command, code, text }`; the first one, `refuseMissingTarget` of `lib/commands/append.js`, answers `NO [TRYCREATE]` to an APPEND or REPLACE to a missing mailbox, and `getPendingTarget()` there finds the target name of a pending literal)
- `server.commandChecks` (`(connection, parsed)`, run in `processQueue` after the state and mailbox name checks and before the handler, return `{ command, code, text }` to refuse a command whatever plugin handles it, e.g. UIDONLY's `BAD [UIDREQUIRED]`, MESSAGELIMIT's PARTIAL range check) `server.rangeLimits` (`(connection, parsed, range)`, called through `connection.limitRange()` by FETCH, STORE, COPY, MOVE and UID EXPUNGE after they resolved their sequence set, can return fewer messages, MESSAGELIMIT keeps the highest UIDs, from the highest down, and sets `parsed.highestFirst` so that MOVE and UID EXPUNGE send their EXPUNGE responses in that order while COPY and MOVE still copy in UID order) and `server.searchLimits` (`(connection, messages, query)`, can return a shorter list of messages for SEARCH, SORT and THREAD to look at, or throw an error with `imapResponse` and a `responseCode` list; the query tree is the one `commands/handlers/search.ts` builds). `src/vanished.ts` turns EXPUNGE notifications into VANISHED responses for QRESYNC and UIDONLY
- output handlers that must see responses after every other plugin changed them (UIDONLY turns FETCH into UIDFETCH, MESSAGELIMIT adds its code next to the codes of other plugins) push themselves to `server.outputHandlers` in a `server.once('pluginsLoaded', ...)` listener, like the ACL command wrappers. `src/load-plugins.ts` emits `pluginsLoaded` once every plugin is loaded, listeners run in plugin load order
- `server.parserOptions`: parser options of plugins for every connection (e.g. BINARY sets `literal8` and adds to `allowSection`), merged under `connection.parserOptions`. The raw input reader in `onData` recognizes `~{n}` literal8 markers and refuses them unless the command allows literal8 (the `literal8` command option)

Plugins must stay self-contained: if a plugin is not loaded, no trace of it should remain (e.g. messages get no MODSEQ without CONDSTORE). Plugin names are validated and deduplicated by `src/load-plugins.ts`, and ENABLE and CONDSTORE work in any load order (QRESYNC loads both through `plugin.requires`). The ACL plugin wraps the enforced commands (also those of other plugins, like MOVE and UID EXPUNGE) and the STORE flag handlers on `pluginsLoaded`, so it works in any load order too; the owner (`aclOwner` option, default `testuser`) bypasses the enforcement. `src/command-states.ts` lists only RFC 3501 core commands; a plugin passes the options of its own commands as the third argument of `setCommandHandler(command, handler, { states, noArguments, mailboxArguments, astringArguments, searchCriteria, sequenceSet, noExpunge, literal8, noPipelining, appendMessage })`: `astringArguments` lists other astring positions (user names, ACL identifiers), where `processQueue` turns the parser's null for a NIL atom back into an atom with `restoreNilAtoms` (src/arguments.ts), as it does for mailbox names and search criteria; a STORE handler with `astringValues` (X-GM-LABELS) gets the same for its values and accepts literals; `searchCriteria` is the argument position where SEARCH style criteria start and `sequenceSet` the position of an argument with message sequence numbers (FETCH, STORE, COPY, MOVE, REPLACE; used for the RFC 3501 5.5 sequence number check and by UIDONLY), `noExpunge` marks commands during which EXPUNGE responses are not allowed (FETCH, STORE, SEARCH, SORT, THREAD), so notifications are held back and clients may pipeline after them, `literal8` lets the command take `~{n}` literals (RFC 3516), and `noPipelining` refuses the command with BAD when the client sent more input after it (STARTTLS, COMPRESS: the layer change would otherwise apply to input sent before it), and the commands that arrived in the same read are refused too, without running (`connection.isPipelinedAfterRefusal()`). Wrapping an existing command without options keeps its settings.

Per connection hooks for plugins that change the wire format: `connection.parserOptions` and `connection.compilerOptions` are passed to the `imap-handler` parser and compiler, `connection.importMailboxName(name)` converts every mailbox name argument (the `mailboxArguments` positions) to the modified UTF-7 storage name and throws a BAD error for an invalid name, and `connection.exportMailboxName(path)` converts a storage name for output. Every response that carries a mailbox name must convert it: either call `exportMailboxName` (LIST, LSUB, NAMESPACE), or put `{ type: 'MAILBOX', value: storageName }` in the attributes (also inside lists, like the MAILBOX correlator of ESEARCH), which `send` converts for the receiving session and sends as an atom or a string (STATUS, QUOTAROOT, METADATA, needed for notifications that go to several sessions). `matchFolders` takes the export function as its third argument. A command whose mailbox argument has no fixed position calls `importMailboxName` itself (GETMETADATA, ESEARCH). `connection.searchCharset` fixes the SEARCH charset of a session: a CHARSET argument is then BAD, and SORT/THREAD accept only that charset; `connection.defaultSearchCharset` only changes the charset assumed without CHARSET (IMAP4rev2: UTF-8). UTF8=ACCEPT and IMAP4rev2 set these through `src/utf8-session.ts`, which computes the UTF-8 state of a session from `connection.enabled`, so both plugins work in any load order. `connection.disabledSearchKeys` and `connection.disabledStatusItems` (Sets, or null) remove SEARCH keys and STATUS items from a session (BAD), `connection.addedStatusItems` allows STATUS items for one session only, `connection.number64` makes the `number64` SEARCH argument type (LARGER, SMALLER) take 63-bit values, and `connection.parserOptions.number64` (imap-handler) literal sizes and partial ranges (IMAP4rev2 sets both), `connection.messageGlobal` makes message/global parts encapsulate a message in BODYSTRUCTURE and section numbers (`resolveNode(tree, path, global)`, `embeddedMessage()` in `mimeparser.ts`), and `connection.getFlags(message)` can be replaced per connection (IMAP4rev2 leaves out `\Recent`). A plugin that needs another one lists its name in `plugin.requires` (UTF8=ACCEPT requires ENABLE), `src/load-plugins.ts` loads it first.

Other modules: `mimeparser.ts`, `bodystructure.ts`, `envelope.ts`, `addressparser.ts` produce BODYSTRUCTURE/ENVELOPE data from raw messages; `encoded-words.ts` decodes RFC 2047 encoded words for SEARCH header keys, SORT and THREAD; `sorting.ts` (collation, base subject, sent date, address and Message-ID values, and the search step) and `threading.ts` (THREAD command, ORDEREDSUBJECT and REFERENCES) back the SORT, SORT=DISPLAY and THREAD=* plugins; `smtp-listener.ts` is the optional SMTP listener (built on the optional `smtp-server` peer dependency) that appends incoming mail to INBOX; `cert/` holds the self-signed localhost cert used for STARTTLS and `secureConnection` (embedded through the generated `src/cert.ts`).

## Tests

Tests use `node:test` and `node:assert`. The usual pattern (`test/*.test.ts`): inside a `describe` block, `const ctx = setupServer(() => ({ plugins, storage }))` (from `test/helpers/`) registers hooks that start a fresh server on a random port before every test and close it afterwards. `ctx.run(cmds, resp => ...)` replays IMAP command strings (binary strings) through `src/mock-client.ts` (response and literal framing shared with the test helpers and `compare/` lives in `src/framing.ts`), which behaves like a compliant client: it waits for the tagged response before the next command, sends literal data only after the `+` continuation, sends the next list entry as continuation data when the server asks for one (DONE, SASL responses), and closes the connection after the last command. Tests assert on the full response transcript, preferably with line anchored regexes (`/^A3 NO \[TRYCREATE\]/m`). `ctx.server` is the live server for inspecting state. Because ports are random, test files run in parallel. Keep helpers out of the top level of `test/`, since every `test/*.js` file runs as a test file.

Test layers:

- protocol tests per command or plugin (`test/<command>.test.ts`), table driven strictness checks in `test/conformance.test.ts`
- multi-session behaviour (EXPUNGE timing, flag updates, IDLE, `\Recent`) in `test/sessions.test.ts` and the RFC 2180 scenarios in `test/multi-access.test.ts`, using `openSession()` from `test/helpers/session.js` for interleaved connections; RFC 2683 recommendations in `test/implementation-recommendations.test.ts`
- a real client end to end in `test/imapflow.test.ts` (ImapFlow, all plugins and none)
- MIME fidelity and golden BODYSTRUCTURE/ENVELOPE wire forms (checked against Dovecot) in `test/mime-fidelity.test.ts` with fixtures in `test/fixtures/mime/`
- parser level tests of the MIME code in `test/mime.test.ts`

Every transcript from `ctx.run` and `openSession` goes through `test/helpers/validate-responses.ts` before the test sees it: CRLF framing and literals, the RFC 3501 section 9 shape of tagged, untagged and `+` responses (status text is required, so every OK/NO/BAD/BYE response, including untagged ones with only a response code, must carry human readable text; no 8-bit outside literals, nz-numbers for FETCH/EXPUNGE, FETCH lists in pairs), and ImapFlow's response parser. A failure there means ImapKit sent something a compliant client can not parse, so fix the server rather than the check. `test/fuzz.test.ts` replays mutated commands under the same guardrail; on failure it prints `FUZZ_SEED`, the iteration and the input, and `FUZZ_SEED=<n> FUZZ_ITERATIONS=<n> node --import tsx --test test/fuzz.test.ts` reproduces or widens a run.

## Comparing with Dovecot

`compare/` holds a development aid, not a test suite. It replays the same IMAP commands against ImapKit and a real Dovecot 2.4 server and shows where the responses differ. Use it when building or fixing a feature, to see what RFC compliant input and output look like in practice. Dovecot is the most spec compliant server around, but it has its own bugs, quirks and extensions. Treat a difference as a hint to check the RFC (fetched from rfc-editor.org), not as proof that ImapKit is wrong, and do not copy Dovecot behavior that the RFC does not require.

- `npm run dovecot:start` / `npm run dovecot:stop` (`compare/dovecot.sh`, also `status`, `restart`, `logs`) manage a long-running Docker container `imapkit-dovecot` (image `dovecot/dovecot:2.4.4`) with plain IMAP on `127.0.0.1:32143`. `compare/dovecot.conf` is mounted as a drop-in. It allows cleartext login, turns off FTS so SEARCH is plain substring matching, stops auto-creating special-use mailboxes, and turns on QUOTA (count driver, 10M and 1000 messages), APPENDLIMIT (5M), ACL (vfile) and METADATA for comparison. Overrides: `IMAPKIT_DOVECOT_IMAGE`, `IMAPKIT_DOVECOT_PLATFORM` (forcing `linux/amd64` on Apple Silicon does not work), `IMAPKIT_DOVECOT_PORT` (also read by compare.ts), `IMAPKIT_DOVECOT_HOST`.
- The compare tool speaks COMPRESS=DEFLATE: after a tagged OK to `COMPRESS DEFLATE` a session compresses and the output is compared decompressed (`compare/scenarios/compress.txt`).
- `npm run compare -- compare/scenarios/fetch.txt`, or `node --import tsx compare/compare.ts -c 'SELECT INBOX' -c 'FETCH 1 BODYSTRUCTURE'`. `--plugin IDLE,MOVE` loads ImapKit plugins, `--target imapkit|dovecot` runs one side only, and `--json` gives machine readable output (handy for Claude); `--help` lists all options.
- Every run starts an in-process ImapKit on a random port and logs into Dovecot as a brand-new user (static passdb, password `pass`). That user is seeded from the same storage JSON through a hidden setup connection: CREATE, SUBSCRIBE, and APPEND with flags and internaldate. Only personal namespaces with `/` as separator are seeded, `\Recent` is dropped, and a warning is shown if Dovecot assigns different UIDs than the storage specifies.
- Scenario files (`compare/scenarios/*.txt`) hold one step per line. A plain line is a command and gets an automatic tag (`A1`, `A2`, ...). `2: CMD` runs on session 2 (sessions open and log in on first use). `> DONE` is sent verbatim with no tag and waits for the tagged response of the command left open by a continuation (IDLE, AUTHENTICATE). `!wait 500` pauses. `#` starts a comment. In commands, `\r\n` becomes CRLF and `{file:path}` / `{file+:path}` become a literal with the file's contents (path relative to the scenario file, sample messages in `compare/messages/`), `~{file:path}` / `~{file+:path}` a literal8 with the file's octets as they are (binary samples in `compare/messages/literal8/`, kept out of `test/mime-fidelity.test.ts`). `compare/scenarios/sort-thread.txt` runs against `compare/storage-sort-thread.json` (see the comment at its top), messages with tricky subjects, dates, addresses and references. `$USER` / `$PASS` expand per server, for use with `--manual-login`, and `$UIDVALIDITY` to the last UIDVALIDITY the server sent (for `SELECT ... (QRESYNC ($UIDVALIDITY 1))`). Synchronizing literals wait for the `+` continuation.
- Both outputs are normalized before they are compared:
    - Dovecot's `(0.001 + 0.000 secs)` timings are removed.
    - The human readable text of OK/NO/BAD/BYE and of `+` continuations is dropped (`--keep-text` keeps it).
    - UIDVALIDITY values are masked, also inside COPYUID and APPENDUID.
    - LIST/LSUB responses and flag lists are sorted, and quoted mailbox names that are valid atoms are unquoted. `--exact` turns this sorting and unquoting off.
- Known differences that are not ImapKit bugs:
    - CAPABILITY lists (Dovecot advertises many extensions, and some, like IMAP4rev2 or CONDSTORE, change its output once enabled).
    - Lowercase vs uppercase BODYSTRUCTURE strings.
    - Dovecot reports INTERNALDATE in UTC.
    - Dovecot sends `* OK [CLOSED]` when switching mailboxes, ImapKit only with CONDSTORE or QRESYNC loaded (RFC 7162 section 3.2.11), or after `ENABLE IMAP4rev2`. Dovecot also sends it before a BAD for invalid SELECT arguments, ImapKit does not, as the command did not run.
    - Mod-sequences differ: ImapKit gives every message changed by one STORE its own MODSEQ. Dovecot sends HIGHESTMODSEQ on more tagged responses (NOOP, APPEND) than RFC 7162 requires.
    - The first session to select a seeded mailbox sees the messages as `\Recent` in Dovecot.
    - Dovecot's IDLE notifications can arrive late, so put a `!wait 1000` after the step that triggers them.
    - Messages expunged by another session (`compare/scenarios/multi-access.txt`, run with `compare/storage-multi-access.json`): Dovecot still stores flags on them and returns NIL for their bodies, keeps them in UID FETCH and refuses UID COPY and UID MOVE with `NO [EXPUNGEISSUED]`, and sends BYE for a deleted mailbox only at the next command. ImapKit follows the RFC 2180 strategies listed in the README "Multiple sessions" section.
    - NOTIFY (`compare/scenarios/notify.txt`): Dovecot sends its events later, ImapKit while the other session's command runs. Dovecot sends no LIST with OLDNAME for RENAME (RFC 5465 section 5.4), leaves UID out of unsolicited flag FETCH responses (section 5.1 MUST), reports the changes a session made itself (section 5 SHOULD NOT), accepts mailbox events with `selected` (section 6.1), lists only the unsupported events in `BADEVENT` without parentheses (sections 3.1 and 8), and does not support MailboxMetadataChange and ServerMetadataChange although it has METADATA (REQUIRED by sections 5.6 and 5.7).
    - CREATE `a/b` makes `a` a normal mailbox in ImapKit and a `\Noselect` level in Dovecot (RFC 3501 section 6.3.3 allows both).
    - LSUB flags: Dovecot sends `()` for every subscribed name, ImapKit sends the LIST flags of existing mailboxes without `\Noselect`.
    - MODSEQ and HIGHESTMODSEQ values, Dovecot assigns its own mod-sequences when the user is seeded.
    - Extended LIST: ImapKit always sends `\HasChildren`/`\HasNoChildren`, and sends STATUS items in the requested order. Dovecot omits `CHILDINFO` for a mailbox that matches the selection criteria itself (RFC 5258 section 3.5 asks for it), accepts an empty pattern list `LIST "" ()` and `(SPECIAL-USE RECURSIVEMATCH)` (both break the RFC 5258 / RFC 6154 grammar), and takes the last of two different `STATUS` return options.
    - PREVIEW text can differ for HTML and multipart messages: Dovecot keeps the HTML `<title>`, puts a space for inline tags, drops unknown entities, and also uses attachments and other text/* types. Dovecot also accepts `PREVIEW.PEEK` (not in RFC 8970) and drops the connection on `PREVIEW (LAZY LAZY)`, which the grammar allows.
    - IMAP4rev2 (after `ENABLE IMAP4rev2`): Dovecot still answers SEARCH with a SEARCH response (RFC 9051 section 6.4.4 requires ESEARCH), refuses `SEARCH CHARSET` like UTF8=ACCEPT does (RFC 9051 section 6.4.4 allows it), accepts CHECK, LSUB and the RFC822 FETCH items (not in the RFC 9051 grammar, ImapKit answers BAD), and describes message/global as a basic part (RFC 9051 section 7.5.2 treats it like message/rfc822). Dovecot accepts partial ranges and LARGER/SMALLER values above 32 bits in IMAP4rev1 sessions and above 63 bits in IMAP4rev2 sessions. Its SELECT LIST response has no attributes.
    - METADATA: Dovecot sends every value as a literal, lists DEPTH results in its own order, accepts `()` as an empty entry or option list, atoms as values and `/shared` in SETMETADATA, refuses server annotations with `[CANNOT]`, has no `/private/specialuse`, sends no unsolicited METADATA responses, and moves instead of copies the annotations of INBOX on RENAME (RFC 5464 section 4.1 says copy).
    - SORT and THREAD: Dovecot accepts charsets other than US-ASCII and UTF-8, `REVERSE REVERSE`, a literal charset and a quoted threading algorithm, which ImapKit refuses per RFC 5256 section 5. Dovecot sends `* THREAD ` with a trailing space when nothing matches, against the thread-data grammar.
    - Sent dates (RFC 5256 section 2.2): for a Date header with an invalid or missing time Dovecot uses the internal date, ImapKit uses 00:00:00 of that date, and Dovecot reads a zone like `+2360` as an offset where ImapKit uses UTC.
    - Dovecot's quota limits come from its config (STORAGE 10240, MESSAGE 1000), it refuses SETQUOTA and puts every mailbox under its quota root. ImapKit has no limits unless the `quota` option sets them, and only INBOX and the personal namespaces belong to its quota root.
    - Dovecot does not support OBJECTID.
    - COMPRESS: Dovecot answers `NO [COMPRESSIONACTIVE]` to a second COMPRESS and `NO` to an unknown mechanism, RFC 4978 section 3 lists both as BAD (ImapKit sends `BAD [COMPRESSIONACTIVE]`). Dovecot advertises COMPRESS=DEFLATE only after login.
    - ACL: Dovecot lists rights in another order, names the compare user instead of `testuser` as the owner in GETACL, answers MYRIGHTS for mailboxes that do not exist and ignores extra MYRIGHTS arguments, and silently ignores STORE and EXPUNGE in a mailbox that is READ-ONLY because of the ACL. Dovecot lets the owner change its own rights (except `a`), ImapKit answers `NO [CANNOT]`. Dovecot sends MYRIGHTS twice for `RETURN (MYRIGHTS MYRIGHTS)` (RFC 5258 section 3 counts a repeated option once).
    - MULTIAPPEND to the selected mailbox: ImapKit sends one EXISTS per message, Dovecot one for all.
    - CATENATE: Dovecot accepts relative-path URLs (`;UID=1`), which RFC 5092 section 7.2 forbids, and appends an empty string for a part that does not exist, where ImapKit answers `NO [BADURL]` (RFC 4469 section 4.1).
    - REPLACE: ImapKit sends EXISTS before EXPUNGE like the RFC 8508 section 3.2 example, Dovecot the other way round. When the target is another mailbox, Dovecot sends the EXPUNGE only with the next command. Dovecot accepts REPLACE after EXAMINE and expunges from the read-only mailbox, ImapKit answers NO. Dovecot answers BAD to `REPLACE *`, which the seq-number grammar allows.
    - `STATUS (APPENDLIMIT)` is BAD in Dovecot, RFC 7889 section 3.1 adds it for every server with APPENDLIMIT.
    - Dovecot accepts `APPEND` of a message with 8-bit header fields before `ENABLE UTF8=ACCEPT`, RFC 9755 section 4 requires NO (ImapKit follows the RFC).
    - After `ENABLE UTF8=ACCEPT` Dovecot still sends 8-bit ENVELOPE strings as literals, ImapKit quotes valid UTF-8 (both are valid).
    - BINARY: Dovecot sends decoded base64 and quoted-printable data as a literal8, ImapKit only data with NUL (RFC 3516 section 4.3 says SHOULD use a string otherwise). Dovecot accepts `BINARY[]`, `BINARY[n.MIME]` and `BINARY[0]`, which ImapKit refuses, fails every BINARY item of a message with `NO [UNKNOWN-CTE]` when any of its parts has an unknown encoding, sends `* n FETCH (UID n)` before such a NO, answers `NO [PARSE]` for broken quoted-printable (ImapKit decodes it as RFC 2045 section 6.7 suggests), and stores a binary message/rfc822 part base64 encoded, which RFC 2046 section 5.2.1 forbids.
    - Dovecot does not support PARTIAL (RFC 9394) or MULTISEARCH. It accepts `RETURN (UPDATE)` and `PARTIAL` for SORT without advertising CONTEXT=SORT, and sends the updates of a SORT context with context position 0, which RFC 5267 section 4.3.3 only allows for SEARCH. It cancels the known tags of `CANCELUPDATE "known" "unknown"` and answers NO, ImapKit cancels nothing then. It accepts a literal in CANCELUPDATE, which takes quoted strings only.
- `test/compare.test.ts` covers the tool's parsing, normalizing and seeding against ImapKit only, so `npm test` stays Docker-free.
